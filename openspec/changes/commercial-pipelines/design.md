# Design: Commercial Pipelines (advisor-managed funnels and stages)

## Technical Approach

Additive advisor CRUD over the accepted `pipelines` + `pipeline_stages` DDL (`infra/migrations/004_commercial_crm.up.sql:43-72`), closing the read-only Embudo gap. Today the only route is `GET /v1/demo/pipeline` (`api/composition_wu8_mvp.py:320-322`) served by `CrmReadService.pipeline` (`api/queries/crm_reads.py:107-114`) over `PostgresCrmReadRepository.pipeline_views` (`api/adapters/postgres_crm_reads.py:163-183`, pipelines ordered by `created_at, id`, stages with `lead_count` ordered by `position, id`); the "Embudo" view (`web/app/page.tsx:1473-1498`, `ViewKey "pipeline"` at line 58, fetched via `demo-api.ts` `pipeline()` at line 224 + `parseCrmPipelineResponse` in `contracts/runtime-v1.ts:504-525`) renders kanban columns with zero management controls; and no write endpoint exists. Six new commands in a NEW module `api/application/pipeline_commands_wu19.py` on the `CrmCommandBase` template (`api/application/crm_commands_wu5.py:87-212` — reserve idempotency → scoped write → audit + outbox → commit): `pipeline.create` (name + initial stages), `pipeline.rename` (name only), `pipeline.stage.create` (name + position), `pipeline.stage.rename` (with the agent-name warning), `pipeline.stage.reorder` (up/down swap), `pipeline.stage.delete` (fail-closed BLOCK when leads reference the stage). A NEW router `api/routes/pipeline_wu19.py` (`build_pipeline_router`) mounts additively in `api/composition_wu8_mvp.py` beside the simulator/calendar/agent `include_router` lines (lines 399-415); the accepted `GET /v1/demo/pipeline` stays byte-identical. No schema migration: the DDL already carries every needed constraint (`UNIQUE (pipeline_id, position)`, `UNIQUE (pipeline_id, name)`, composite FKs, `ON DELETE RESTRICT` throughout), and `demo_seed_key` NULL already distinguishes advisor rows — so there is explicitly NO `012` migration. The three owner-resolved decisions (2026-10-14) are baked in: delete-with-leads BLOCKs fail-closed; rename warns-and-keeps-by-name with agent escalation on disappearance; reorder is up/down buttons now, DnD later.

## Architecture Decisions

| Decision | Choice | Rationale |
|---|---|---|
| **New command module (not an extension)** | `api/application/pipeline_commands_wu19.py` importing `CrmCommandBase`, `CrmCommandDenied`, `CrmCommandValidationError` from `crm_commands_wu5.py`; six classes with `operation = "pipeline.create" / "pipeline.rename" / "pipeline.stage.create" / "pipeline.stage.rename" / "pipeline.stage.reorder" / "pipeline.stage.delete"`, `audit_resource_type = "pipeline"` / `"pipeline_stage"`, PascalCase outbox types (`PipelineCreated`, `PipelineRenamed`, `PipelineStageCreated`, `PipelineStageRenamed`, `PipelineStageReordered`, `PipelineStageDeleted`; audit action is `crm.{operation}` via the base) | `crm_commands_wu5.py` owns the inbound/transition/follow-up lifecycle (4 commands); pipeline administration is a distinct bounded surface with its own guard (agent-name warning) and pre-check (lead count). A new file keeps the accepted WU5 file byte-stable and mirrors the `configuration_commands_wu17.py` / `agent_signal_bindings_commands.py` precedent (one module per surface). |
| **No pipeline delete command (settled)** | This unit ships NO `pipeline.delete`: pipelines are created and renamed only. Stage delete is the only destructive op | The proposal left "pipeline delete denied via the RESTRICT chain (or command pre-check — settled at design)" open; settling it as out-of-scope removes the ambiguity honestly. A pipeline row with stages/leads is already undeletable by construction (`pipeline_stages_pipeline_account_fk` + `leads_pipeline_account_fk`, both `ON DELETE RESTRICT`), so no route means no new denial path to pin. |
| **Position semantics** | Ordering column is `pipeline_stages.position` (`integer >= 0`, `UNIQUE (pipeline_id, position)`, `004:61,68`). Create defaults to append (`COALESCE(max(position), -1) + 1` per pipeline); optional explicit `position` shifts siblings `>= target` up by the insert count in the same transaction. Reorder swaps the stage with its adjacent neighbor only (up = `position - 1`, down = `position + 1`); already-first/already-last is a no-op success `{moved: false}` (idempotent-friendly) | Append-at-end needs no sibling writes; the bounded up/down swap is the owner-resolved reorder shape. The no-op edge keeps replay/double-click safe. |
| **UNIQUE-safe renumbering** | Swap via a temp slot (`max(position) + 1`, always `>= 0` so the CHECK holds): A → temp, B → A-old, temp-holder → B-old, all under the pipeline `FOR UPDATE` lock in one transaction. Insert-at-position uses `UPDATE … SET position = position + k WHERE pipeline_id = %s AND position >= %s` (adding a constant to distinct values preserves distinctness, so no transient UNIQUE violation), then INSERTs at `target` | Postgres enforces UNIQUE per-statement (constraints are not deferrable here), so a naive two-row swap or low-to-high shift would collide mid-statement. The temp-slot / constant-offset techniques never produce a duplicate within any single statement. |
| **Pipeline-row locking** | Every stage op first `SELECT … FROM pipelines WHERE id = %s AND client_account_id = %s FOR UPDATE`; the write, lead-count pre-check, and renumber all run on the same cursor before the base's single commit | Serializes concurrent reorders/creates/deletes per pipeline, so two advisors cannot interleave position assignments and the delete pre-count cannot race a concurrent insert past the check (the `ON DELETE RESTRICT` FKs backstop either way). |
| **Agent-name guard: warn, never deny** | `AGENT_KNOWN_STAGE_NAMES = QUALIFY_STAGE_NAMES + (VISIT_STAGE_NAME,)` = `{"Calificado", "Simulador: visita calificada", "Visita agendada"}` (`conversation_agent.py:56-58`). `pipeline.stage.rename` and `pipeline.stage.delete` compute `agent_name_warning = (old_name ∈ KNOWN and new_name ∉ KNOWN-per-pipeline-after-write)` and return it in the payload + audit extra; the command NEVER denies on this ground. `pipeline.stage.create` sets the flag when it restores a missing known name (`agent_name_restored: true`) | Renames must stay advisor-sovereign (owner decision 2); the warning is advisory. The by-name resolver (`_stage_id_for_name`, `agent_wu14.py:500-508`: `SELECT s.id … JOIN leads … WHERE s.client_account_id = %s AND l.id = %s AND s.name = %s`) keeps working untouched — it simply resolves or returns NULL. |
| **Agent interplay: omission, not escalation** | When the agent's target name is gone, `ConversationAgent.analyze` leaves `qual_stage_id`/`visit_stage_id` as NULL and `_derive_actions` (`conversation_agent.py:361-364, 374-377`) emits NO `transition_lead` — the rest of the plan (register_interest/follow-up/event) proceeds unchanged and the policy reason falls back to `search_match` (no-transition) instead of `search_match_with_transition`. No new behavior is added; `execute_transition` by id (`TransitionLeadStageCommand`, `crm_commands_wu5.py:456-514`) is untouched throughout | This is the U14-pinned unresolvable-name behavior (`api/test_conversation_agent.py:261-272`: "unresolvable stage → no transition action", never a guessed id). The design documents the existing path rather than inventing an escalation flow. |
| **Seed interplay** | Advisor rows are created with `demo_seed_key = NULL`. Reset (`mvp_reset.sql:20-36`) and both seeds (`mvp_seed.sql:95-111`, `mvp_seed_008.sql:118-120`) DELETE strictly by `(client_account_id, demo_seed_key)` pairs behind the ownership gate (`mvp_reset.sql:8-17`), so NULL-marked advisor rows survive by construction. The harness preclean identifies the NULL-marked simulator stage (`ensure_simulator_stage`, `simulator_wu9.py:99-120`, also NULL by design at position 1 when free) by name/position scope, never by blanket NULL-marker deletion | Marker-pair deletes cannot match NULL rows (`NULL IS DISTINCT FROM` semantics + explicit pair lists); the only NULL-row hazard is a sloppy preclean, which the name/position scoping rules out. Note the simulator stage occupies position 1 only when no seed `Calificado` (pos 1) exists — new advisor stages use `max + 1`, never a hardcoded position, so they cannot collide with it. |
| **No migration (012 stays free)** | Highest applied migration is `011_agent_custom_field_writes`; no `012` file is created. Every needed invariant already exists in 004: `position >= 0` CHECK, `UNIQUE (pipeline_id, position)`, `UNIQUE (pipeline_id, name)`, composite FKs `(pipeline_id, client_account_id)` and `(stage_id, pipeline_id, client_account_id)` all `ON DELETE RESTRICT`, `leads.status IN ('new','qualified','won','lost')` | A migration file with zero DDL would be dishonest churn. If a later unit needs advisor-row markers or pipeline-level UNIQUE names, `012` is the next free number. |
| **Contacts/properties untouched** | `contacts` and `properties` hold NO foreign key to stages or pipelines (004:7-41); only `leads` references both. Stage delete therefore needs exactly one pre-check (`leads` count); pipeline rename needs none | Grounds the pre-check scope: one `SELECT count(*) FROM leads WHERE stage_id + account` per delete, nothing else. |

## Contracts, Invariants, and Flow

New endpoints on `build_pipeline_router` (all under `/v1/demo`, all return `X-Correlation-Id` + `correlation_id`; unknown keys → 400 via the `_console_body` pattern (`agent_wu14.py:319-335`); forged/foreign/ghost ids → 404 non-enumerating via a `_denial` mapping over a local `_NOT_FOUND_REASONS` frozenset mirroring `agent_wu14.py:136-142` extended with `pipeline_not_found_in_scope` / `stage_not_found_in_scope`; idempotency keys are `console:{account}:{entity}:{key}` per `_console_key`, `agent_wu14.py:282-292`):

- `POST /pipelines {name, stages?: string[], idempotencyKey?}` → `_console_ok(correlation, "pipeline", {resource_id, name, stages:[{stage_id, name, position}]})`. Blank name → 400 (mirrors the DDL `CHECK (btrim(name) <> '')`, `004:47`); duplicate pipeline names in one account are ALLOWED (no such UNIQUE exists — honest asymmetry with stage names, documented). Stages are created `0..n` in order.
- `PUT /pipelines/{pipeline_id} {name, idempotencyKey?}` → `{resource_id, name}`; moves no leads/stages by construction (name-only UPDATE).
- `POST /pipelines/{pipeline_id}/stages {name, position?, idempotencyKey?}` → `{resource_id, pipeline_id, name, position}`; omitted `position` appends at `max + 1`; explicit `position` clamps to `[0, count]` then shifts siblings; same-pipeline name clash → denied `stage_name_already_exists` (pre-check + UNIQUE backstop `pipeline_stages_pipeline_name_unique`).
- `PUT /stages/{stage_id} {name, idempotencyKey?}` → `{resource_id, name, agent_name_warning}`; clash → denied as above; warning when an agent-known name disappears from the pipeline.
- `POST /stages/{stage_id}/move {direction: "up" | "down", idempotencyKey?}` → `{resource_id, position, moved}`; strict enum, unknown direction → 400.
- `DELETE /stages/{stage_id}` (body `{idempotencyKey?}`) → `{resource_id, deleted: true}` on empty stages; `lead_count > 0` → denied `stage_has_leads` with `{"lead_count": n}` metadata, zero effects, one redacted denial audit (WU6 pattern, `crm_commands_wu5.py:242-269`).

Flow: route validates shape → `_console_key` → command `execute` (reserve → `SELECT pipeline … FOR UPDATE` → pure-rule validation → write + lead-count/agent-name checks → base appends `audit_records` + `outbox_events` → commit). Reads-after-write reuse the accepted `pipeline_views` unchanged (`crm_reads.py:107`, `postgres_crm_reads.py:163-183`).

Invariants: `position >= 0` and dense per pipeline after every op (`UNIQUE (pipeline_id, position)` holds in every intermediate statement); stage names unique per pipeline (`UNIQUE (pipeline_id, name)`); every write tenant-scoped (`client_account_id` predicate first) + idempotent (replay returns the canonical stored payload, `crm_commands_wu5.py:139-162`); a stage with leads is never deleted (pre-count denial + `leads_stage_pipeline_account_fk … ON DELETE RESTRICT`, `004:93-94`); an agent-known rename/delete never denies, only warns; advisor (`demo_seed_key IS NULL`) rows are invisible to reset/seed pair-deletes.

Command `_apply` sketch (reorder swap; same cursor as the reservation):

```python
async def _apply(self, context, cur, intent):
    account_id = context.client_account.id
    await cur.execute(
        "SELECT id FROM pipelines WHERE id = %s AND client_account_id = %s FOR UPDATE",
        (intent["pipeline_id"], account_id))
    if await cur.fetchone() is None:
        raise CrmCommandDenied("pipeline_not_found_in_scope")
    ordered = await self._ordered_stages(cur, account_id, intent["pipeline_id"])
    # ... locate index, neighbor; edge -> {"moved": False}
    tmp = max(p for _, p in ordered) + 1
    await cur.execute("UPDATE pipeline_stages SET position = %s WHERE id = %s", (tmp, a_id))
    await cur.execute("UPDATE pipeline_stages SET position = %s WHERE id = %s", (a_pos, b_id))
    await cur.execute("UPDATE pipeline_stages SET position = %s WHERE id = %s", (b_pos, a_id))
    return {"resource_id": a_id, "position": b_pos, "moved": True,
            "agent_name_warning": False, "correlation_id": context.correlation_id}
```

Delete pre-check (inside the same locked transaction, before the DELETE):

```sql
SELECT count(*) AS n FROM leads
 WHERE client_account_id = %s AND stage_id = %s;
-- n > 0 -> CrmCommandDenied("stage_has_leads", {"lead_count": n})
DELETE FROM pipeline_stages
 WHERE id = %s AND client_account_id = %s AND pipeline_id = %s;
```

## Testing Strategy

Harness scenarios (StubModelProvider, offline; every effect via the new routes/commands, never hand-inserted): P1 pipeline round-trip — create with initial stages → rename (leads/stages unmoved, verified via `GET /v1/demo/pipeline` before/after) → per-account isolation (cross-account ids invisible, forged/ghost ids 404 non-enumerating). P2 stage lifecycle — append-at-end (`position = max + 1`), insert-at-position with sibling shift, rename (same-pipeline duplicate denied; agent-known rename returns `agent_name_warning: true` and the UI badge shows), up/down reorder reflected in kanban order (`position, id` read untouched). P3 delete fail-closed — stage with leads denied `stage_has_leads` with scoped denial audit + zero effects; empty stage deletes; concurrent-shape check (lock + pre-count in one transaction). P4 agent safety — rename away `Calificado` makes `analyze` omit `transition_lead` for affected leads (policy reason `search_match`, U14 behavior, no handoff emitted); restoring the name restores transitions; `execute_transition` by id succeeds throughout. P5 seed/reset interplay — reset after advisor edits removes only marker-owned rows (the four pair-lists in `mvp_reset.sql:20-36`); user (`demo_seed_key IS NULL`) pipelines/stages survive; the NULL-marked simulator stage is precleaned by name/position scope. P6 idempotency — replayed create/rename/reorder/delete keys return the canonical stored result with zero extra effects; stub-offline runs the full harness with no API key. P7 regression — WU14/WU15/WU16/WU17/WU18 harnesses (and earlier suites) stay green on their own bases; `python -m compileall -q api infra`, `npm.cmd exec vitest run`, `tsc --noEmit`, web build (`README.md:124-142`).

## Risks and Rollback

Fail-closed delete racing lead creation: mitigated — the delete holds the pipeline `FOR UPDATE` lock and pre-counts `leads` inside the same transaction as the DELETE, so a concurrent lead insert either lands first (delete denies) or second (fails the stage FK/composite scope); `leads_stage_pipeline_account_fk … ON DELETE RESTRICT` (`004:93-94`) backstops either way. Agent name-resolution breakage on rename: mitigated by the rename-time `agent_name_warning` against `AGENT_KNOWN_STAGE_NAMES` plus the agent's existing no-guess omission on unresolvable names (U14-pinned, `test_conversation_agent.py:261-272`); no silent misrouting by construction. Position UNIQUE collisions on concurrent reorders: mitigated by the single-transaction temp-slot swap under the pipeline lock. Simulator-stage NULL-marker confusion in preclean: mitigated by name/position scoping (never blanket NULL-marker deletion). Insert-at-position off-by-one: mitigated by clamping to `[0, count]` and the constant-offset shift (distinctness-preserving). Rollback: no new tables by design — remove `pipeline_commands_wu19.py`, `pipeline_wu19.py`, the one `include_router` line, the contract/UI additions, and the new harness + units; accepted WU5–WU18 surfaces and all existing data untouched by construction (no migration to roll back, no seed edits).
