# Design: Agent Custom Field Writes (signal auto-fill)

## Technical Approach

Additive, optional signal-driven auto-fill on top of the accepted `configuration` (WU17) surface, closing the one piece of debt it deliberately left open (D4). The agent may write a custom-field value only through a NEW proposed action type `set_custom_field_value` that REUSES `SetLeadCustomFieldValueCommand` (`api/application/configuration_commands_wu17.py:272`, operation `configuration.custom_field.value.set`, `_coerce_value` at line 77) unchanged; the value is never model prose — it is a deterministically extracted signal from a closed, code-owned catalog, resolved against a per-account, producer-scoped binding, gated by the existing allowlist. Two things are closed today: the allowlist WRITE path `UpdateFieldAllowlistCommand` (`api/application/agent_commands_wu16.py:691`, operation `agent.allowlist.update`) still validates against `ALLOWLIST_COLUMNS = frozenset({"stage_id","status","selected_property_id"})` (line 56) and its `_apply` inserts only `column_name` (no `field_definition_id`) — debt D4, already anticipated by the `010_configuration` schema (`agent_field_allowlist.field_definition_id` + composite FK) and by `load_field_allowlist` (`api/adapters/postgres_agent_console.py:114`) returning fixed ∪ custom names; and `PROPOSED_ACTION_TYPES` (`api/domain/agent_draft.py:23`) has no type for writing custom values. Migration `011_agent_custom_field_writes` persists a `signal → field_definition_id` binding table and widens the `agent_policy_matrix.action_type` CHECK from 7 to 8 types; no binding rows are seeded, so install is zero behavior change (no bindings ⇒ the agent emits no `set_custom_field_value`). The console mounts a new "Fuentes del agente" section additively on the existing `build_agent_router` (`api/routes/agent_wu14.py:430`); the `app.include_router(build_agent_router(...))` line stays byte-identical.

## Architecture Decisions

| Decision | Choice | Rationale |
|---|---|---|
| **Binding table (OD-3 settled)** | `agent_signal_bindings` — one row per `(client_account_id, signal_key)`: `signal_key text CHECK IN ('phone','email','presupuesto_max','barrio','tipo_propiedad','fecha_objetivo','medio_de_contacto')`, `field_definition_id uuid NOT NULL`, composite FK `(field_definition_id, client_account_id) → custom_field_definitions (id, client_account_id) ON DELETE CASCADE`, `UNIQUE (client_account_id, signal_key)`, `demo_seed_key`; no producer column (deferred until automations exist) | One binding per account × signal is the settled owner shape. | **Policy matrix CHECK 7→8** | `ALTER TABLE agent_policy_matrix DROP CONSTRAINT agent_policy_matrix_action_type_check` then re-ADD admitting `'set_custom_field_value'` as the 8th type (the inline 009 CHECK is auto-named `agent_policy_matrix_action_type_check`, same convention `010` used for `agent_field_allowlist_column_name_check`) | The 009 CHECK is a literal list; a new action type cannot pass it, and the settings PUT (`_validate_matrix`, `agent_commands_wu16.py:184`) + the matrix upsert (`_apply`, line 222) must accept the 8th row the console now renders. Drop/re-add is the only honest widening. The down-file restores the 7-type CHECK. |

| **Signal catalog + extraction (pure helper)** | New `api/application/agent_signals.py`: `SIGNAL_KEYS = frozenset({...7 keys...})` + `extract_signals(interpretation, body) -> dict[str, Any]`. `presupuesto_max ↔ criteria["budget_max"]`, `barrio ↔ criteria["city"]`, `tipo_propiedad ↔ criteria["property_type"]`, `fecha_objetivo ↔ criteria["preferred_date"]` — all already parsed by `model_provider._extract` (`api/application/model_provider.py:280`)/`_validate_criteria`; `phone`/`email` from a small deterministic regex over the raw `body`; `medio_de_contacto` = `"phone"` if phone resolved else `"email"` if email resolved else absent. Unresolvable ⇒ key absent, never guessed | The four criteria-backed signals are already deterministic and validated (`budget_max` positive number, `city` bounded string, `property_type` ∈ `PROPERTY_TYPES`, `preferred_date` ISO-8601); no double-parse. Phone/email are NOT in `INTERPRETATION_KEYS`/`CRITERIA_KEYS`, so a bounded body regex is the only source — and absence is the honest default (same grounding discipline as `send_reply`). |
| **Planner seam** | `ConversationAgent.__init__` (`conversation_agent.py:112`) gains one injected `bindings: Callable[..., Any] | None = None` (alongside `search`/`availability`/`upcoming`/`kb_lookup`/`price_read`/`last_interest`/`stage_id_for_name`) returning the account's bindings `[{signal_key, field_definition_id, field_name}]`. `analyze` calls it once; when `not bindings`, extraction is skipped entirely (owner decision 2a). `_derive_actions` (`conversation_agent.py:306`) gains `signal_values`/`bindings`/`allowed_lead_fields` and emits `set_custom_field_value` only when `lead_id is not None` AND the signal resolved AND a binding exists AND `field_name ∈ allowed_lead_fields` | The planner stays pure (no SQL/HTTP); the binding callable + allowlist frozenset are injected facts. Extraction is a single pure call gated on non-empty bindings, so zero bindings ⇒ no extraction cost and no action. `lead_id is None` (no lead) ⇒ no lead-write action, mirroring `transition_lead`. |
| **Policy verdict (OD-1 settled)** | `set_custom_field_value` added to `AUTO_ACTION_TYPES` (`agent_policy.py:51`); `evaluate()` (`agent_policy.py:162`) verdict shape unchanged | AUTO means the action rides the intent's existing verdict (e.g. `search_match` auto-executes it); `default_verdict` (`postgres_agent_console.py:77`) and `ALL_CONSOLE_ACTION_TYPES`/`CONSOLE_ACTION_TYPES` (`AUTO_ACTION_TYPES ∪ {HANDOFF_ACTION}`) auto-grow to 8, so the fallback verdict is `auto` with no new `evaluate()` branch. |
| **Dispatch reuse** | `_dispatch_actions` (`agent_wu14.py:336`) gains a `set_custom_field_value` branch that re-checks `params["field_name"] in allowed` (deny `lead_field_not_allowed` otherwise — defense-in-depth, allowlist may have changed since analyze) and calls `custom_field_set_cmd.execute_set(context, lead_id=draft.lead_id, field_id=params["field_id"], value=params["value"], idempotency_key=key)` with the per-action key `agent-draft:{draft.id}:{index}` | No fork of the WU17 command: `_coerce_value` (`number`/`date`/`select∈choices`/`text`) stays the single authority, and a `select` field whose choices do not include the signal's native string fails truthfully (`outcome=denied`/`invalid`) rather than guessing a mapping. The `SetLeadCustomFieldValueCommand` instance is already wired as `custom_field_set_cmd` (`agent_wu14.py:515`). |
| **Allowlist write widening (D4)** | `UpdateFieldAllowlistCommand` (`agent_commands_wu16.py:691`) accepts fixed columns ∪ defined `custom_field_definitions.name` for the account; `_apply` resolves non-fixed names to `field_definition_id` via a scoped in-transaction SELECT and stores both `column_name` and `field_definition_id`; an undefined name raises `CrmCommandValidationError` | Same command, same operation, same DELETE-then-INSERT — the only change is the validity domain and persisting `field_definition_id`. The dual-column gate `_TRANSITION_WRITES = {"stage_id","status"}` (`agent_wu14.py:140`) is untouched, and the `010` composite FK/dual CHECK already accepts the widened rows. |
| **Binding CRUD commands** | New `api/application/agent_signal_bindings_commands.py`: `CreateSignalBindingCommand` (`agent.signal_binding.create`, upsert `ON CONFLICT (client_account_id, signal_key) DO UPDATE SET field_definition_id`) and `DeleteSignalBindingCommand` (`agent.signal_binding.delete` by `signal_key`) — both `CrmCommandBase`. `_apply` validates `signal_key ∈ SIGNAL_KEYS` and that `field_definition_id` is a defined field in scope (`custom_field_not_found_in_scope` otherwise) | Editing a binding is delete + create (honest CRUD, no `agent.signal_binding.update`). Validation lives in the command (not the route), tenant-scoped by the composite FK and the in-transaction scope SELECT, matching the allowlist custom-name pattern. |
| **Console section "Fuentes del agente"** | Routes on `build_agent_router`: `GET /agent/signal-bindings` (`_console_ok(correlation, "signal_bindings", {count, items:[{signal_key, field_definition_id, field_name, field_type}]})`), `POST /agent/signal-bindings {signal_key, field_definition_id}`, `DELETE /agent/signal-bindings/{signal_key}`. ## Contracts, Invariants, and Flow

New endpoints on the agent router (all under `/v1/demo`, all return `X-Correlation-Id` + `correlation_id`; unknown keys → 400; forged/foreign ids → 404 non-enumerating; strict enums via `runtime-v1.ts` parsers):

- `GET /agent/signal-bindings` → `_console_ok(correlation, "signal_bindings", {count, items:[{signal_key, field_definition_id, field_name, field_type}]})`.
- `POST /agent/signal-bindings {signal_key, field_definition_id}` → `_console_ok(correlation, "signal_binding", {signal_key, field_definition_id, field_name, field_type})` (upsert); unknown `signal_key` → 400, foreign/unknown `field_definition_id` → 404 (`custom_field_not_found_in_scope`).
- `DELETE /agent/signal-bindings/{signal_key}` → `_console_ok(correlation, "signal_binding", {signal_key, deleted: true})`; unknown `signal_key` → 400.
- `PUT /agent/lead-fields` (existing route, `agent_wu14.py:1430`) widens to accept defined custom names — stores `field_definition_id`; undefined custom name → 400; seeded `{stage_id, status}` transition still succeeds.

Flow: `POST /agent/signal-bindings` → `CreateSignalBindingCommand` (reserve → scope-check field → upsert → audit `agent.signal_binding.create` + outbox → commit). `POST /agent/analyze` → `load_signal_bindings` returns bindings; if none, `extract_signals` is skipped and no `set_custom_field_value` is emitted; otherwise `extract_signals(interpretation, body)` resolves signals, `_derive_actions` emits `set_custom_field_value` for each signal that resolved AND is bound AND allowed, `evaluate()` returns AUTO for it (riding the intent verdict), and `_dispatch_actions` executes it through `SetLeadCustomFieldValueCommand.execute_set` (coercion + type validation + `select∈choices` enforced by `_coerce_value`, `UNIQUE (lead_id, field_id)` upsert). Denial (allowlist) records `outcome=denied, reason=lead_field_not_allowed` truthfully in `execution_result` (overlap-denial precedent), draft still finalizes.

Invariants: one binding per account × signal (`UNIQUE (client_account_id, signal_key)`); every binding's `field_definition_id` belongs to the same `client_account_id` (composite FK); deleting a definition cascades its bindings (no orphan bindings); a `set_custom_field_value` is emitted only for a resolved signal + existing binding + allowlisted field + non-null `lead_id`; the value is always `_coerce_value`-validated text (never model prose, never guessed); every console write tenant-scoped + idempotent (`console:{scope}:{entity}:{key}`); per-action dispatch keys stay `agent-draft:{draft_id}:{index}`; `execution_mode='agent_policy'` attribution rules unchanged.

SQL shape (011 UP — next free number after 010; DOWN reverses each part in reverse order):

```sql
CREATE TABLE agent_signal_bindings (
    id uuid PRIMARY KEY,
    client_account_id uuid NOT NULL REFERENCES client_accounts (id) ON DELETE RESTRICT,
    signal_key text NOT NULL CHECK (signal_key IN
      ('phone','email','presupuesto_max','barrio','tipo_propiedad',
       'fecha_objetivo','medio_de_contacto')),
    field_definition_id uuid NOT NULL,
    demo_seed_key text,
    created_at timestamptz NOT NULL DEFAULT now(),
    updated_at timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT agent_signal_bindings_id_account_unique UNIQUE (id, client_account_id),
    CONSTRAINT agent_signal_bindings_account_signal_unique UNIQUE (client_account_id, signal_key),
    CONSTRAINT agent_signal_bindings_demo_seed_key_unique UNIQUE (demo_seed_key),
    CONSTRAINT agent_signal_bindings_field_account_fk
        FOREIGN KEY (field_definition_id, client_account_id)
        REFERENCES custom_field_definitions (id, client_account_id) ON DELETE CASCADE
);
CREATE INDEX agent_signal_bindings_account_idx
    ON agent_signal_bindings (client_account_id, signal_key);

-- policy matrix: widen the 7-type CHECK to admit the 8th action type.
ALTER TABLE agent_policy_matrix DROP CONSTRAINT agent_policy_matrix_action_type_check;
ALTER TABLE agent_policy_matrix ADD CONSTRAINT agent_policy_matrix_action_type_check
    CHECK (action_type IN ('send_reply','register_interest','create_follow_up',
                           'transition_lead','create_event','reschedule_event',
                           'handoff_to_human','set_custom_field_value'));
```

    "tipo_propiedad", "fecha_objetivo", "medio_de_contacto",
})

def extract_signals(interpretation, body):
    """Deterministic {signal_key: value}; unresolvable keys are absent.

## Testing Strategy

Harness scenarios (StubModelProvider, offline; every effect via the accepted command surfaces, never hand-inserted): C1 binding CRUD — create/list/delete a `signal_key → field` binding per account; unknown `signal_key` → 400; foreign/unknown `field_definition_id` → 404; cross-account invisible; deleting the bound `custom_field_definitions` cascades the binding away. C2 deterministic extraction — for each of the 7 signals, the resolved value is byte-deterministic from the validated interpretation/body; a signal with no resolvable value emits no action (never a guessed value). C3 AUTO execution writes value — with a binding + allowlist + resolved signal on an `auto` conversation, the draft auto-executes `set_custom_field_value` through `SetLeadCustomFieldValueCommand`, writing a `lead_custom_field_values` row (`UNIQUE (lead_id, field_id)` upsert) with `number`/`date`/`select∈choices`/`text` coercion enforced. C4 allowlist gates the write — removing the custom name from `PUT /agent/lead-fields` denies the action with `lead_field_not_allowed` recorded truthfully in `execution_result`. C5 no-binding ⇒ no action — an account with zero bindings emits no `set_custom_field_value` and writes nothing (zero behavior change; regression oracle on the WU17 base). C6 D4 closed — `PUT /agent/lead-fields` accepts a defined custom name (stores `field_definition_id`, FK satisfied), rejects an undefined name; the seeded `{stage_id, status}` transition still succeeds; `_TRANSITION_WRITES` untouched. C7 forged/ghost ids non-enumerating on the new routes. C8 stub runs C1–C6 offline with no API key (`langchain_openai` never imported). C9 regression — WU14/WU15/WU16/WU17 harnesses stay green on their own bases; `compileall`, typecheck, `npm test`.

## Risks and Rollback

Wrong auto-write corrupting a field — mitigated by the closed catalog (no free-writes), `_coerce_value` validation (a `select` value must be `∈ choices`, `number`/`date` must coerce), and the allowlist gate (a field the advisor has not allowed is denied). A `select` field whose choices don't match the signal's native value fails truthfully rather than guessing a mapping. Binding drift after a field edit/delete — mitigated by the composite FK and `ON DELETE CASCADE` (a deleted definition clears its bindings), and a `choices` change re-validates on the next write through the existing command. Policy matrix CHECK widening — the drop/re-add is the declared honest widen; the seeded/default matrix keeps `set_custom_field_value` = `auto` and no console surface regresses. Extraction scope — gated on non-empty bindings (owner decision 2a), so accounts without bindings pay nothing and emit nothing. Rollback: run `011` down on a reset demo base + remove `agent_signal_bindings_commands.py`, the `load_signal_bindings` read, the `agent_signals.py` helper, the `bindings`/`_derive_actions`/`_dispatch_actions`/`AUTO_ACTION_TYPES` additions, the console slice, and the contract/UI additions, and revert the allowlist-write widening; accepted WU5–WU17 surfaces and prior data untouched by construction (no binding rows exist outside the unit).
